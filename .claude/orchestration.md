# AI 오케스트레이션 — 이 저장소의 구현 절차

**설계는 Research → Plan → Implement 와 랄프 루프로 목업까지, 구현은 이 파이프라인으로.**
(2026-10-30 작성자 결정)

근거는 작성자가 직접 돌린 시험이다 — `pipeline-test-report.docx` (유효 실행 9회,
`github.com/dpcivl/agent-pipeline-lab`). 아래 수치와 규칙은 거기서 왔다.

## 서브에이전트를 나누는 기준

역할 이름으로 나누지 않는다. **BE / FE 로 쪼개면 같은 모델끼리 일을 주고받는 것과 같다.**
셋 중 하나에 해당할 때만 나눈다.

1. **독립적인 검증이 필요할 때** — 리뷰·보안은 구현 맥락 없이 diff 만 읽어야 한다
2. **컨텍스트 분리가 필요할 때** — 파일 수십 개를 읽은 흔적을 메인에 남기지 않는다
3. **서로 독립인 작업을 병렬로 할 때** — 공유하는 게 없을 때만

**결정론적 검사는 서브에이전트가 아니라 메인이 직접 돌린다.** 린트 · 타입 · 빌드 ·
링크 · 마크다운 · 비밀값. 같은 스크립트가 같은 결과를 내므로 맡길 이유가 없다.

서브에이전트끼리 직접 대화하지 않는다. 모든 지시와 보고는 메인을 거친다(허브).
수정 라운드에서는 **같은 에이전트를 `SendMessage` 로 이어 부른다** — 다시 부르면
맥락을 처음부터 읽어서 8천 토큰이 더 든다.

### 결정론적 게이트 (4단계, 메인이 직접)

```bash
pnpm lint && pnpm format:check && pnpm test:all && pnpm build && pnpm check:md && pnpm links
```

`pnpm test:all` 이 vitest 와 pytest 를 차례로 돌린다 (`pnpm test` · `pnpm test:py` 로
따로도 된다). mermaid 블록을 넣었으면 `pnpm mermaid:render` 를 먼저.
`server/scratch-ui/src/` 를 고쳤으면 `pnpm scratch:build`.
비밀값 검사는 보안 에이전트가 아니라 여기서 한 번 더 한다.

### 테스트 러너 (2026-10-31~)

**두 러너가 있다.** 작성자가 「구현 · 테스트 병렬로 진행해야 한다」고 정해서 들였다.
그 전까지는 러너가 없어 3단계의 test-writer 를 띄우지 못했다.

| 러너 | 대상 | 테스트 위치 | 명령 |
| --- | --- | --- | --- |
| vitest | 블로그 쪽 순수 JS (`scripts/` 의 발행 검사 등) | `tests/*.test.mjs` | `pnpm test` |
| pytest | 서버 파이썬 (`server/*.py`) | `tests/server/test_*.py` | `pnpm test:py` |

- **pytest 는 uv 로 띄운다** — `uv run --with pytest pytest`. 저장소에 venv 를
  커밋하지 않고 두 기기에서 같은 명령으로 돌리려고 그렇게 했다. uv 가 없는 기기에는
  설치해야 한다 (macOS `brew install uv` · Windows `winget install astral-sh.uv`)
- **서버 파이썬은 표준 라이브러리만 쓴다.** pytest 는 개발 기기에만 있고 512MB
  Lightsail 인스턴스는 건드리지 않는다
- vitest 는 `tests/**/*.test.mjs` 만 본다 (`vitest.config.ts`). Astro 컴포넌트는
  이 러너로 돌리지 않는다
- 테스트 파일에서 `describe` · `it` · `expect` 는 **import 해서 쓴다.** 전역으로
  켜지 않았다 — eslint 설정에 vitest 전역을 더하지 않으려고

**남은 차이.** 보고서가 결과를 믿을 근거로 꼽은 「사람이 정한 숨긴 수용 테스트」는
작성자가 미리 테스트를 숨겨뒀을 때만 성립한다. 러너는 생겼지만 그 관행은 아직 없다.
지금 품질 근거는 게이트 + 리뷰 3종 + 위 두 러너다.

## 심각도와 자율 처리 규칙

보고서 5.2. **실제 결함이 남은 원인은 탐지가 아니라 판정이었다.**

- **재현된 실패는 major 이상** — 조건이 드물어도 실제로 재현한 오류(500 · 시작 실패 ·
  데이터 손상 · 빌드 깨짐)는 major
- **두 역할 이상이 지적하면 심각도와 무관하게 수정**
- **수정 비용이 작은 minor 는 수정 라운드가 열릴 때 묶어서 함께 수정**
- **운영 조건을 계획서에 넣는다** — 두 기기 동시 편집, 재시작, CSP, 느린 회선

blocker · major 가 있으면 수정 후 재검토. minor 만 남으면 기록하고 넘어간다.

## 사람 게이트 — 두 번만

보고서 4.1 에서 **개입 모드가 승인 도장이 됐다.** 메인이 권장안을 붙여 묻자 사람이
30초 만에 그대로 골랐다. 그래서 묻는 방식을 바꾼다.

- **G1 (계획 승인)** — 계획과 목업의 차이, 쓰기 범위, 예상 비용을 적는다
- **G2 (커밋 전)** — 「진행할까요」로 묻지 않는다. **직접 확인할 항목을 체크리스트로**
  내고(화면 흐름 · 오류 화면 · 핵심 동작), 사람이 확인한 결과를 적어야 넘어간다
- **선택을 물을 때는 권장안을 먼저 붙이지 않는다.** 지적 목록과 재현 여부만 내고
  사람이 고른 뒤에, 물으면 그때 의견을 낸다
- 시점을 늘리지 않는다. 늘릴수록 습관적 승인이 는다

> 작성자 메모(2026-10-23)의 보고 형식 예시에는 `(추천: …)` 가 붙어 있었다. 보고서 4.1
> 이 그 방식의 문제를 보여줬으므로 **추천을 떼는 쪽으로 바꿨다.**

## 보고 형식 (고정)

서브에이전트와 메인이 사람에게 내는 보고는 이 칸을 그대로 쓴다. 작성자 메모의 형식이다.

```
## 결론
한 줄. 그리고 「내가 할 일」 한 줄

## 결정 요청
번호. 선택지만. 추천은 붙이지 않는다

## 설계와 다른 점
[추가] / [변경] / [안 함] 과 이유

## 검증 결과
게이트 · 리뷰 · 화면 확인 결과

## 확인하지 못한 것
무엇을, 왜. 사람이 직접 봐야 할 것

## 변경 파일

## 되돌리기
```

**「설계와 다른 점」과 「확인하지 못한 것」을 비워 내지 않는다.** 보고서에서 결함이 가장
먼저 드러난 경로가 이 두 칸이었다.

## 지시 프롬프트 쓰는 법

보고서 5.4.

- **문서 내용을 붙이지 말고 경로와 읽을 부분을 짚는다** —
  「`server/scratch-ui/mockups/compose-plan.md`, 특히 1·2절」
- **수정 지시에는 결정까지 담는다** — 무엇을, 어떤 문구로, 어디에. 반영하지 않을 지적도 적는다
- **병렬로 일하는 쪽의 영역을 적는다** — 「`src/` 는 implementer 가 쓰는 중이니 건드리지 마라」
- **검토 범위는 커밋 해시 범위로.** 재검토는 「해결 여부와 이번 diff 의 새 문제」로 좁힌다

## 쓰기 범위

각 에이전트 정의에 적혀 있다. **구현에게 테스트 쓰기 권한을 주지 않는다** — 테스트를
고쳐서 통과시키려 한다.

지금은 프롬프트로만 막는다. 시험에서는 hook 으로 강제했지만 여기서는 안 걸었다.
어기는 일이 생기면 그때 `.claude/settings.json` 에 `PreToolUse` 훅을 넣는다.

**`.orchestration/` 는 gitignore 대상이다.** 보안 점검 보고서가 고치기 전의 취약점을
적어두는데, 이 저장소는 공개다.

## 예산 — 언제 쓰고 언제 안 쓰나

| 항목 | 시험 기준값 |
| --- | --- |
| 기능 하나 (API + 화면 + 테스트 + 문서) | $4.8~8.6 · 15~41분 |
| 수정 라운드 1회 | +$1.2~3.1 · +3~22분 |
| 서브에이전트 1회 호출 고정 비용 | 약 8천 토큰 (이어 부르면 90% 절감) |
| 비용 구조 | 메인 49% · 리뷰 1라운드가 가장 비쌈 |
| 파이프라인 없이 Opus 한 세션 | 약 1.6배 |

토큰의 약 92%가 **맥락을 다시 읽는 데** 쓰인다. 그래서:

- **기능을 작게 나눠 돌린다.** `compose-plan.md` 의 4단계처럼
- **글 쓰는 일에는 쓰지 않는다.** 포스트 발행 · 메모 정리 · 오타 수정은 지금처럼 메인 혼자
- **한 파일 고치는 일에도 쓰지 않는다.** 고정 비용이 일보다 크다
