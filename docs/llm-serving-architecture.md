# LLM 을 제품에 붙일 때 어디에 두는가

2026-09-24 에 정리. 블로그에 AI 검색 기능을 넣을지 따져보다가, "노션이나 슬랙에
붙은 AI 는 GPU 서버를 따로 두고 부르는 건가" 라는 질문에서 시작했다.

결론부터: **GPU 를 직접 사는 곳은 소수다.** 대부분은 남의 GPU 를 부른다. 그리고
"제공사 API 직접" 과 "우리 GPU" 사이에 중간 단계가 있고, 기업 대부분이 거기 있다.

## 네 개의 칸

| 칸 | 데이터가 가는 곳 | 주로 쓰는 곳 |
| --- | --- | --- |
| 제공사 API 직접 (`api.anthropic.com` 등) | 제공사 서버 | 스타트업 · 일반 SaaS |
| **클라우드 경유** (Bedrock · Azure OpenAI · Vertex) | **그 클라우드의 지정 리전 안** | **기업 대부분** |
| 클라우드 VPC 내 전용 배포 | 우리 VPC 안 | 규제가 강한 곳 |
| 완전 온프레미스 | 우리 데이터센터 | 망분리 · 폐쇄망 |

가운데 두 칸이 존재하는 이유가 핵심이다. **기업이 원하는 건 GPU 소유가 아니라
계약과 통제다.** 데이터가 학습에 안 쓰인다는 보장, 지정한 국가 리전 밖으로 안
나간다는 보장, 로그가 어디 남는지에 대한 통제 — 이게 확보되면 GPU 를 살 이유가
없다.

**GPU 를 직접 사는 건 인터넷 자체가 막혀 있을 때다.** 망분리 환경에서는 API
호출이라는 선택지가 애초에 없어서 온프레미스 외에 답이 없다.

## 왜 대부분 GPU 를 안 사는가

| | 월 비용 (대략) |
| --- | --- |
| GPU 인스턴스 1대 (A10G 24GB급) | $700–800 |
| 같은 작업을 호스팅 API 로 (중소 규모) | $1–50 |

GPU 는 **놀고 있어도 돈이 나간다.** 요청이 없는 새벽에도 시간당 과금이고, API 는
안 부르면 0원이다. 이 둘이 역전되려면 하루 수백만 요청 수준의 꾸준한 트래픽이
필요하다. 거기까지 가는 회사는 드물다.

품질도 문제다. 자체 호스팅으로 감당 가능한 크기의 모델은 프런티어 모델보다 눈에
띄게 못하다.

> 숫자는 2026-09 기준 어림값이다. 판단에 쓸 때는 그 시점 요금을 다시 볼 것.

## 자체 호스팅을 하는 이유 네 가지

1. **데이터가 밖으로 나가면 안 될 때** — 가장 큰 이유. 공공 · 금융 · 국방
2. **물량이 아주 많고 일정할 때** — 위의 역전점을 넘긴 경우
3. **지연 · 위치 제약** — 공장 현장, 폐쇄망, 엣지
4. **자사 데이터로 파인튜닝한 모델**이 있을 때

한국 SI 에서는 1번이 그대로 일거리가 된다. 요구사항 문서에 "국내 리전", "망분리
구간 내 처리" 같은 게 박혀 오고, 그게 아키텍처를 결정한다.

## 자체 호스팅할 때의 구조

```
[앱 서버]  ──HTTP──▶  [추론 서버 · GPU]
 웹 · API              vLLM / TGI / SGLang
 싸고 여러 대           비싸고 적은 대수
```

**GPU 는 앱 서버에 있지 않다. 별도 서버 또는 클러스터다.** 이유가 셋이다.

- GPU 머신은 비싸다. 거기서 웹 서버까지 돌리면 비싼 자원을 낭비한다
- **증설 축이 다르다.** 앱 서버는 접속자 수에, 추론 서버는 토큰 처리량에 맞춰 늘린다
- 추론 서버 하나가 여러 앱을 먹여살린다. 사내 챗봇 · 문서 검색 · 분류가 같은 클러스터를 쓴다

## 어느 칸이든 같은 것

```
백엔드  ──HTTP──▶  추론 엔드포인트
```

**앱 백엔드는 모델을 품지 않는다.** 항상 HTTP 로 추론 서비스를 부른다. 그리고 그
서비스가 `api.anthropic.com` 이든, 사내 GPU 의 vLLM 이든, `localhost` 의 Ollama 든
**호출하는 코드는 거의 같다.** 주소와 인증 방식만 바뀐다.

OpenAI 호환 형식이 사실상 표준이 된 덕분이다. 직접 부딪힌 지점이기도 하다 —
[AI 라우팅 #2](../src/data/blog/ko/ai-routing-02-reading-the-code.md) 에서 로컬
Ollama 에 보내는 요청이 OpenAI API 형식이라는 걸 알게 됐다.

**그래서 작은 서버에 Ollama 를 올려보는 게 헛일이 아니다.** 맨 아래 칸의 축소판이고,
배우는 건 모델이 아니라 그 주변이다 — 타임아웃, 재시도, 스트리밍, 동시 요청 제한,
죽었을 때 뭘 할지. 그건 칸이 바뀌어도 그대로 쓴다.

## 실무에서 자주 쓰는 절충

**생성은 API, 임베딩은 자체 호스팅.**

임베딩 모델은 수십 MB 라 GPU 없이도 돌고, **호출 횟수가 압도적으로 많다** (문서 전부
+ 질의 전부). 이건 자체 호스팅이 확실히 이긴다. 반대로 생성은 횟수가 적고 품질이
중요하니 API 가 낫다.

| | 크기 (int8) | 어디서 |
| --- | --- | --- |
| all-MiniLM-L6-v2 (22M) | 약 23MB | 브라우저에서도 돈다 |
| multilingual-e5-small (118M) | 약 120MB | 한국어 됨 |
| 생성 모델 0.6B q4 | 약 500MB | CPU 로는 초당 5–15 토큰 |

## 이 블로그에 적용한다면

같은 계산에서 나온 답이라 구성이 위 절충과 같다.

- **검색** — Pagefind (정적 인덱스, 클라이언트, 0원). 부족하면 빌드타임 임베딩
- **요약** — 빌드 때 미리 만들어 JSON 으로 커밋. 런타임 비용 0
- **생성이 실시간으로 필요하면** — 버튼을 눌렀을 때만, 속도 제한과 일일 상한을 걸고

**검색창 경로에 느린 로컬 모델을 물리면 안 된다.** 0.6B 모델이 200토큰 답변을
내는 데 20–40초 걸린다. 대신 **속도가 안 중요한 일**에 쓰면 작은 모델이 제값을 한다
— 댓글 스팸 분류, 빌드타임 요약, 태그 추천.
