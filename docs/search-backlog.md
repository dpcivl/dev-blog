# 검색 개선 백로그

질문을 링크로 바꿔주는 기능의 남은 숙제. 측정해서 확인한 것만 적는다.
근거는 전부 `scripts/embed/testset.jsonl` (긍정 35 · 부정 15) 기준이다.

## 지금 어디까지 왔나

```
모델        text-embedding-3-large · 1024차원 · 조각 1,297개
운영점      관문 0.05 · 보정 0.15 · 하한선 0.47
성적        맞힘 28/35 · 1등 27/35 · 헛답 0/15
응답        199ms (질문 임베딩) + 2ms (내적) + 1ms (낱말)
비용        월 1만 질의에 $0.03
```

낱말을 섞어서 얻은 것: 같은 헛답 수에서 맞힌 수가 2문항 올랐다.

| 헛답 | 혼합 | 벡터만 |
| --- | --- | --- |
| 0/15 | 28/35 | 26/35 |
| 1/15 | 28/35 | 26/35 |
| 2/15 | 29/35 | 28/35 |
| 3/15 | 30/35 | 30/35 |

---

## 1. 두 신호가 같은 데서 같이 틀린다 — 제일 큰 숙제

낱말 검사를 넣으면 "없는 주제" 를 잘 거를 줄 알았는데 기대만큼은 아니었다.
글의 낱말을 피해서 물으면 **벡터도 헛짚고 낱말도 헛짚기 때문**이다. 서로
메워주질 못한다.

남아 있는 실패는 대체로 이런 모양이다.

```
"버튼을 눌렀는데 잠깐 반응이 없을 때 범인을 어떻게 좁혀 갔나"
   정답 「탭을 누르면 화면이 잠깐 얼어붙었다」   벡터 0.364 · 낱말 0.357
   둘 다 낮다
```

**해볼 것**

- **글 쪽에 검색용 낱말을 더해본다.** frontmatter 에 `aliases` 를 두고 조각
  앞머리에 붙여 임베딩한다. 「탭 전환 얼어붙음」 글에 `느려짐 · 렉 · 멈춤` 을
  달아두는 식. 글 본문은 안 건드린다. 89편 중 자주 찾는 20편만 달아도 된다
- **질문을 넓혀본다 (query expansion).** 질문 하나를 두세 가지로 바꿔 각각
  검색하고 합친다. 다만 그만큼 임베딩 호출이 는다
- **제목·소제목만 따로 임베딩해 하나 더 둔다.** 지금은 본문에 묻혀 있다

## 2. 조각을 글 단위로 합칠 때 제일 높은 하나만 쓴다

`read-index.mjs` 의 `search()` 가 글마다 최고 조각 하나만 남긴다. 한 글의
조각 세 개가 고르게 맞은 경우와 하나만 우연히 맞은 경우를 구분 못 한다.

**해볼 것** — 상위 2~3개 조각의 평균을 섞어본다. 측정해보고 나아지면 채택.

## 3. 그래프로 넓히기 (아직 안 해봄)

「벡터로 찾고, 그래프로 넓히기」 를 시도해볼 자리. 글·태그·시리즈를 이어
붙여 벡터가 찾은 글의 이웃을 후보에 넣는다. Neo4j 까지 갈 필요 없이 빌드
때 인접 목록을 만들어 두면 된다.

측정으로 확인된 실패 하나가 여기에 걸린다.

```
"대소문자만 다른 값이 서로 다른 항목으로 세어질 때"
   정답 「더러운 데이터와 스테이징」이 17등
```

정답 글에 「대소문자」 라는 말이 거의 안 나온다. 같은 시리즈의 이웃 글을
후보에 넣으면 올라올 가능성이 있다.

## 4. 모델을 로컬로 되돌릴 여지

채점에서 **bge-m3 가 97% 로 1위**였다 (3-large 는 94%). 지금 3-large 를
쓰는 건 순전히 512MB 인스턴스에 1.13GB 짜리 가중치가 안 들어가서다.

**조건이 바뀌면 다시 본다** — 맥미니를 두고 터널로 부르게 되거나, 서버를
키우게 되거나. `scripts/embed/embedder.mjs` 가 네 모델을 같은 인터페이스로
감싸고 있어서 인덱스 다시 굽고(100초) 모델 이름만 바꾸면 된다.

**같이 다시 재야 하는 것** — 관문 · 보정 · 하한선 세 숫자. 점수의 절대값은
모델 간에 비교가 안 된다.

## 5. 작은 다국어 모델은 아직 안 재봤다

100M 대 다국어 임베딩 모델이 512MB 에 들어가면서 몇 % 나오는지 모른다.
`MODELS` 에 한 줄 더하고 인덱스 한 번 구우면 (약 2분) 답이 나온다.
80% 아래면 볼 것 없고, 90% 가 나오면 서버 자립이 되살아난다.

## 6. 테스트셋이 작고, 한 사람이 만들었다

50문항이고 라벨을 붙인 사람이 한 명이다. 문항 하나가 2~3% 를 움직이므로
지금 숫자들의 오차는 그만큼 크다. 특히 hard 20문항은 **일부러 글의 낱말을
피해서** 쓴 것이라 낱말 검사에 불리하게 기울어 있다.

**해볼 것** — 실제로 들어온 질문을 모아 문항을 늘린다. 다만 질문 로그를
남기는 것은 그 자체로 결정할 일이다 (무엇을 검색했는지가 남는다).

## 7. 인덱스가 글과 어긋날 수 있다

지금은 인덱스를 손으로 굽는다. 글을 올리고 인덱스를 안 구우면 **새 글이
검색에 안 잡히는데 아무 오류도 안 난다.** 조용히 틀리는 쪽이라 위험하다.

**해야 할 것** — CI 에서 릴리스마다 굽는다. `.cache/embeddings/*.cache.json`
을 GitHub Actions 캐시에 두면 바뀐 조각만 다시 부르므로 배포 비용이 0 에
수렴한다. 안 그러면 배포마다 $0.031 이 나간다.

임시 방편으로 `/api/search/health` 가 `builtAt` 과 `chunks` 를 낸다.

## 8. 서버에 Node 가 없다 (2026-10-01에 알게 됨)

`server/search-service.mjs` 는 Node 로 썼는데 **서버에 Node 가 설치돼 있지
않다.** 빌드는 CI 에서 하고 서버는 정적 파일만 서빙해 왔으니 당연한 건데,
1단계를 맥에서만 돌려봐서 몰랐다. 통계 비밀번호 서비스를 올리다가
`status=203/EXEC` 로 드러났다.

**배포 전에 정해야 한다.**

- **Node 를 설치한다** — 디스크 약 100MB, 상주 시 램 60MB 이상.
  패키지를 하나 더 관리하게 된다
- **파이썬으로 옮긴다** — 이미 있고 `generate-stats` 와 비밀번호 서비스가
  쓰고 있다. 하는 일이 내적과 HTTP 중계뿐이라 옮기기 어렵지 않다.
  다만 1,297×1,024 내적을 순수 파이썬으로 하면 느리므로 `array` 나
  `struct` 로 다뤄야 하고, 그래도 느리면 numpy 를 들여야 한다

**먼저 재볼 것** — 파이썬으로 내적이 몇 ms 인지. 맥에서 순수 JS 가 1.8ms
였는데 파이썬이 50ms 를 넘으면 numpy 가 필요하고, 그러면 "가벼워서 파이썬"
이라는 이유가 약해진다.

## 9. 질문이 밖으로 나간다

질문은 OpenAI 로 간다. 이 블로그는 공개 글만 다루므로 문제가 아니지만,
같은 구조를 회사 일에 옮길 때는 여기가 갈림길이 된다. 비용이 아니라
**질문이 나가느냐** 가 기준이다.
